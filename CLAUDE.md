# Algo-Tests: правила работы

Тесты торговых идей на истории ES (e-mini S&P 500), данные Databento. Пайплайн на Python, результаты
публикуются статическим сайтом https://broxyfutures.github.io/algo-tests/.

| Папка | Что это |
|---|---|
| `mp-es-pipeline/` | Market Profile: TPO-профили день / неделя / месяц, типы дня и открытия, композиты, тесты |
| `cot-es-pipeline/` | COT Report и price action. Серия закрыта: преимущества не нашли, оставлено как архив |
| `workspace/` | сайт: папка = страница, `build.py` собирает `index.html` рядом с исходниками |
| `TEST_PLAN.md` | план тестов словами трейдера, статус каждого теста и to-do |
| `TODO.md` | to-do вне тестов: закрыть проект из публичного доступа и прочая безопасность (отложено) |

Общение с трейдером по-русски, просто и коротко. Страницы сайта тоже по-русски, без em-тире и
маркетинговых слов.

## Публикация: сразу в main

Трейдер разрешил (03.10.2026): правки пушатся **прямо в `main`**, без отдельной ветки и PR. Сайт
пересобирается из `main` сам (`.github/workflows/pages.yml`, около 20 секунд).

Порядок для каждой правки:
1. Пересчитать затронутые шаги пайплайна, собрать `python workspace/build.py`.
2. Проверить страницы в браузере (Playwright, `file://`): консоль без ошибок, числа совпадают с выгрузкой,
   ширина телефона без горизонтальной прокрутки.
3. Коммит и `git push origin HEAD:main`. Если облачная сессия выдала свою ветку `claude/...`, работать в ней,
   но пушить в `main` (перед пушем `git fetch origin main`, коммиты поверх свежего `main`).
4. Проверить, что прогон «Сайт тестов» в Actions зелёный. Деплой иногда падает на `actions/deploy-pages` с
   таймаутом OIDC-токена: это не наша ошибка, помогает перезапуск того же прогона.

Netlify (https://algo-tests.netlify.app) остановлен до окончания тестов: в `netlify.toml` стоит
`ignore = "exit 0"`, сборки отменяются. Включить обратно (удалить строку) только по просьбе трейдера, для
финальной выкладки.

CI гоняет только `build.py`, пайплайн не запускает. Поэтому в коммит должны попадать и `results.json`
тестов, и `workspace/assets/data/mp_chart_data.js` (выгрузка шага 12).

## Где мы сейчас

| № | Тест (страница) | Раздел плана | Статус |
|---|---|---|---|
| 1 | Место и тип открытия → тип дня | Opening Types & Day Types | готов |
| 2 | Место открытия → тип открытия | Opening Types & Day Types | готов |
| 3 | Место и тип открытия → тест границ IB | Strong Points | готов, правила 03.10 в TEST_PLAN; плитка «Какая граница протестирована первой?» (1б) готова, порядок внутри блока по минуткам ещё не посчитан |

Очередь: запустить `scripts/08_ib_first_minutes.py` (55 дней с тестом обеих границ в одном блоке, нужны
минутки или ключ Databento), дальше Strong Points 2 (время
экстремумов дня, окна open / drive / mid day / close), Profile Parts 1 и 2 по уровням прошлых профилей,
тест про принятие зоны открытия.

Параллельно идёт разбор ошибок классификации по графику: трейдер приносит даты, где тип дня, точка или
тип открытия выглядят неправильно. Последние правки в `mp-es-pipeline/JOURNAL.md`.

## Как начинать новый тест

1. Наводящие вопросы трейдеру: что считать событием (допуск в тиках), окно времени, исходы, разрезы
   (точка открытия, тип открытия; тип дня как условие не брать, он известен только после закрытия).
   Показать черновые числа при разных определениях, чтобы трейдер выбрал.
2. Согласованные правила записать в TEST_PLAN, показать схемой, только потом считать.
3. Выгрузка в `mp-es-pipeline/scripts/11_test_open_matrix.py` (общая выборка 4050 дней), страница на
   рендерере `mp_open_matrix` с новым значением `outcome`, правила в папке `Правила/`, запись в JOURNAL.

## Что можно пересчитать без сырых данных

Сырые минутки (`cot-es-pipeline/data/es`, 82 МБ) в git **не лежат**: они в `.gitignore` и качаются из
Databento. В репозитории есть `mp-es-pipeline/data/derived/periods_30m.parquet` (30-минутные блоки
всех сессий) и все производные CSV, поэтому:

| Шаг | Нужны минутки | Что делает |
|---|---|---|
| `01_build_periods.py`, `02_build_profiles.py` | **да** | периоды и дневные профили: VA, POC, IB, хвосты, ночь, объём |
| `08_ib_first_minutes.py` | **да** (или ключ Databento, докачает около 55 блоков) | порядок теста границ IB внутри одного блока |
| `04` … `07`, `11`, `12` | нет | недельные и месячные профили, типы дня, композиты, типы открытия, тесты, данные графика |
| `workspace/build.py` | нет | сборка сайта |

В облачной сессии можно менять классификаторы, тесты, сайт и рендереры. Менять размер строки,
правила value area, ночную сессию и объёмные метрики только на машине трейдера, где лежат минутки.
Точность по времени в облаке: 30-минутный блок. Всё, что требует минут (порядок событий внутри блока),
считается на машине трейдера.

Зависимости: `pip install -r mp-es-pipeline/requirements.txt` (pandas, numpy, pyarrow), для проверки
сайта `pip install playwright` (Chromium уже стоит в облачном контейнере).

## Порядок пересчёта

```
01 → 02 → 04 → 05 → 06 → 07 → (08) → 11 → 12 → workspace/build.py
```

`08_ib_first_minutes.py` нужен только тесту 3 (порядок границ внутри одного блока по минуткам), пишет
`data/derived/ib_first_minutes.csv`, который коммитится; без него шаг 11 оставляет исход «в одном блоке».

После правки `config.py` или правил классификации пересобирать с того шага, которого правка касается,
и обязательно 11 и 12, иначе таблицы и график разойдутся с данными.

## Правила, которые нельзя менять молча

- **Параметры профиля заморожены** трейдером: VA 68 %, excess и single prints от 2 блоков TPO,
  последний блок профиля не может дать excess, IB = 2 блока по 30 минут, poor high/low = 2 блока в
  ширину, RTH 09:30–16:00, ETH с 18:00. Всё в `config.py`, описано в `PROFILE_RULES.md`.
- **Любой тест считается в двух режимах блока сразу**: фиксированный (день 2 пт, неделя 4, месяц 8,
  как в терминале трейдера) и адаптивный. Режимы расходятся: точка открытия совпадает у 92 % дней, тип
  дня у 96 %, поэтому доверяем тому, что держится в обоих.
- **Правила замораживаются до просмотра результатов.** Сначала согласовать формулировку с трейдером,
  показать её схемой, и только потом считать. Любое изменение правила: запись в `JOURNAL.md` и в
  `PROFILE_RULES.md` (или в TEST_PLAN, если это правило теста), пересчёт затронутых тестов.
- **Порогов «прошло / не прошло» нет.** Статистика описательная, выводы делает трейдер.
- Типы дня и открытия по Mind Over Markets (Далтон) с поправками трейдера, разделы 6 и 7 в
  `PROFILE_RULES.md`. Ключевые из свежих: Trend проверяется правилом двух блоков на первых десяти
  блоках дня (A…J, ноль нарушений) плюс закрытие в крайних 25 % диапазона, расширение за IB не
  используется; композит закрывает любой день, который в него не вошёл, причин закрытия ровно две:
  миграция VA и сломанная форма.

## Сайт

Структура: главная → инструмент → тест → правила. Текста минимум: трейдер просил без лишних
объяснений и фактов о данных. Стилистика как у проекта cot-report: IBM Plex Mono, углы 2 px, без
градиентов. Дизайн меняется только по просьбе трейдера.

1. **Главная**: шапка «Algo-Tests Workspace» (h1 чуть крупнее, без крошек), подпись и панель плиток
   (Market Profile и плитка «+», ведёт на claude.ai/code). Над панелью тонкая черта (`.tools-wrap`), снизу нет.
2. **Страница инструмента**: шапка, карточка «Tests», под ней карточка «Chart». В Tests плитки разделов
   плана (Opening Types & Day Types, Strong Points, дальше Profile Parts), внутри раздела тесты списком
   друг под другом. Плитки тестов серые (`--surface-2`), при наведении чуть светлее (`--surface-3`).
   Заголовок карточки (`.card-title`) везде отделён от содержимого тонкой чертой.
3. **Страница теста** (рендерер `mp_open_matrix`, исход задаёт `outcome` в results.json: `day`, `open`,
   `ib`): шапка и «Статистика». Переключатели (блок, опора, период и один свой: в тесте 1 Normal
   Variation учитывать / исключить, в тесте 2 Open-Auction внутри VA, в тесте 3 вид исхода) → разделитель →
   общее большое кольцо по всем дням выборки с таблицей по убыванию → разделитель → калькулятор
   «[точки открытия] + [типы открытия] = исход» (мультивыбор, пустой = любые, стиль cot-report), результат
   полосой и плитками по убыванию с разницей к всем дням выборки. Внизу плитка «Правила».
4. **Правила теста**: вложенная папка `Правила/` с `test.md` внутри папки теста (идея, определения,
   исходы, опора, точки открытия, типы открытия). build.py показывает вложенные страницы плитками внизу
   страницы теста.

Названия типов на сайте пишутся полностью: Open-Drive, Open-Test-Drive, Open-Rejection-Reverse,
Double-Distribution Trend, без сокращений вроде O-D или DD-Trend.

«Показать на графике» открывает страницу инструмента (localStorage `mp-chart-pick` + `#pick`): блок, опора и
кнопки фильтров графика (точки, типы открытия, типы дня без NV) встают как в калькуляторе; при своей строке,
своём периоде или в тесте 3 дополнительно передаётся готовый список дней.

Журналы на страницах не показываются, они в `mp-es-pipeline/JOURNAL.md`. Архивные страницы
(`Opening & Day Types` с тестами 1.1, 1.2 и аудитом, COT Report, Footprint) собираются, но скрыты.

Ключи frontmatter, которые понимает `build.py`: `renderer`, `mount_in` (в какой блок встаёт интерактив),
`collapse: [заголовки]` (свёрнутые блоки), `archived: true` (страница собирается, но в списках не видна),
`summary` (подпись плитки), `group` (раздел плана в карточке Tests), `order` (номер теста по плану:
порядок разделов и тестов). Локально сайт открывается и без сервера: `workspace/index.html` по file://.
